# Homebrew tap template

A reusable starting point for a third-party Homebrew tap.
It supports Python CLI formulae, macOS application casks, bottle publishing,
scheduled updates, release-triggered updates, and a generated package catalog.

## Start a tap

1. Create a repository from this template. Name it `homebrew-<tap>` so users can
   install packages through the shorter `<owner>/<tap>` name.
2. In **Settings → Actions → General**, leave the default workflow permissions
   **read-only** and tick *Allow GitHub Actions to create and approve pull
   requests*. Every workflow here declares the write scopes it needs, so a
   read-only default keeps a future workflow that forgets to from inheriting
   them.
3. Replace this introductory section with your tap's name and description.
4. Add a formula or cask with one of the scaffolders below.
5. Run `python3 scripts/gen_readme_packages.py` and commit the generated package
   table with the new Ruby file.

No owner or repository substitutions are required in the scripts or workflows.
They derive the tap name from the Git remote locally and from GitHub Actions at
runtime. Set `HOMEBREW_TAP=owner/tap` to override local detection.

## Install packages

```sh
brew install <owner>/<tap>/<formula>
brew install --cask <owner>/<tap>/<cask>
```

Alternatively, tap the repository first:

```sh
brew tap <owner>/<tap>
brew install <formula>
```

## Add a formula

The formula scaffolder reads PyPI metadata, selects a compatible Homebrew Python,
resolves the dependency tree, pins source distributions and checksums, and emits
`Formula/<name>.rb`. The selected `python@3.x` must be installed
(`brew install python@3.13`): pip evaluates markers and picks compatible releases
for the interpreter it runs under, so resolving with a different one produces a
resource tree that silently does not match the formula's declared Python.

A package or dependency that publishes neither an sdist nor a pure-Python wheel
is refused rather than pinned to a platform wheel that cannot build everywhere.
A PyPI `license` value that is not an SPDX expression (`MIT License`, `UNKNOWN`)
leaves the `TODO-set-SPDX-license` marker with a warning instead of being emitted
as if it were one. `--extras` is recorded in the formula as a
`# homebrew-tap:extras=` comment, which both update workflows read and pass to
`brew update-python-resources --package-name`; without it the first version bump
would re-resolve the base requirement and drop every extras-only resource.

```sh
mise run add-formula <package>
mise run add-formula <package> --extras tui
mise run add-formula <package> --extras tui --check
```

Or run it directly:

```sh
python3 scripts/add_formula.py <package> [--extras a,b] [--python python@3.14] \
  [--version X.Y.Z] [--test-command CMD] [--check] [--tap owner/tap]
```

The generated smoke test assumes the CLI is named after the package and supports
`--version`. PyPI's JSON API does not expose console scripts, so that is a guess:
check the real command and pass `--test-command '#{bin}/<name> version'` when it
differs, or when the package ships no executable at all. Add system dependencies
manually when the package needs libraries that cannot be inferred from Python
metadata.

## Add a cask

The cask scaffolder reads the latest GitHub release, selects a `.dmg`, `.pkg`, or
`.zip`, computes its checksum, and emits `Casks/<name>.rb`.

```sh
GITHUB_TOKEN="$(gh auth token)" mise run add-cask owner/repository
python3 scripts/add_cask.py owner/repository --artifact App-arm64.dmg
python3 scripts/add_cask.py owner/repository --artifact App.pkg --pkg-id com.example.app
python3 scripts/add_cask.py owner/repository --seed
```

For `.dmg` and `.zip` assets, verify the generated `.app` bundle name. An asset
named for one architecture (`App-arm64.dmg`) also gets a matching
`depends_on arch:` stanza, so Homebrew will not install it on the other one. The
cask URL is the one GitHub's API reported, kept percent-encoded, so an asset name
containing a space resolves to the same file the checksum was taken from. A
`.pkg` asset needs `--pkg-id`: Homebrew cannot uninstall an installer payload without an
`uninstall pkgutil:` stanza, and `brew audit --cask --strict` rejects a `pkg`
stanza that has none. The scaffolder prints how to read the identifier out of the
asset. Seed mode uses placeholder release conventions and must be checked against
the first real release.

## Validate changes

```sh
python3 -m unittest discover -s tests -v
python3 scripts/gen_readme_packages.py --check
mise run lint       # every prek hook, across the whole repository
mise run style      # yamlfmt, yamllint, actionlint, action-validator, zizmor
brew test-bot --only-tap-syntax
```

`prek.toml` is the commit-time gate — `mise run hooks` installs it. It covers
file hygiene, `typos`, `markdownlint-cli2`, and the same YAML and Actions
toolchain `mise run style` runs without a hook install; the overlap is
deliberate so neither path is required.

For a formula, also run `brew audit --strict --online <owner>/<tap>/<name>`, install
from source, and run `brew test`. For a cask, run
`brew audit --cask --strict --online <owner>/<tap>/<name>`.

## Automated updates

Two weekly workflows use `brew livecheck` to find and propose formula and cask
updates. A formula bump is audited, built from source, and tested inside the run
that opens the pull request, because a pull request opened with `GITHUB_TOKEN`
does not trigger `tests.yml` — so `brew audit` alone would let a dependency that
fails to build reach a PR looking verified. Bottles still come from `tests.yml`:
close and reopen an automated PR (or push to its branch) to build them before
applying the `pr-pull` label. Two `repository_dispatch` workflows let a package repository request an
update immediately after publishing:

- `update-formula` payload: `{"formula":"name","version":"1.2.3"}`
- `update-cask` payload: `{"cask":"name","version":"1.2.3"}`

The version is optional; the tap uses livecheck when it is omitted. A producer
repository needs a fine-grained token scoped to this tap with **Contents: write**
to call GitHub's repository dispatch API. Store it in the producer repository,
not in the tap.

Bottle publishing follows Homebrew's `brew test-bot` workflow: after CI builds
and uploads bottles, apply the `pr-pull` label to invoke `publish.yml`.

`zizmor.yml` audits the tap's own workflows on every push and pull request and
uploads findings to the Security tab. The dispatch receivers act on
attacker-controllable payloads with a write token, so keep it green.
`gitignore-drift.yml` runs `cobo check` weekly to catch upstream boilerplate
drift; it is a maintenance signal, not a merge blocker.

## Decisions and research

`docs/adr/` holds [MADR](https://adr.github.io/madr/) decision records and
`docs/research/` the notes behind them, both on independent four-digit
sequences. The records shipped here explain why the template is shaped the way
it is — runtime tap-name resolution, Cobo-managed boilerplate, and bumping in
the tap rather than in producer repositories. Keep them, or replace them with
your own once the design stops being yours to inherit.

Agent skills are declared in `skills-lock.json` and restored with
`npx skills experimental_install`; the generated trees are gitignored rather
than vendored.

## Pull request conventions

`check-pr-title.yml` requires
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) titles
and `check-branch-name.yml` requires
[Conventional Branch](https://conventional-branch.github.io/) names, both
reported as a sticky comment on the pull request. `renovate/*` and the
`auto-update/*` branches the bump workflows push are exempt.

## Managed boilerplate

`.gitignore` is generated from GitHub's macOS, Windows, Linux, Visual Studio Code,
Python, and Ruby templates with [Cobo](https://github.com/hasansezertasan/cobo).
Its exact inputs are recorded in `cobo.lock`.

```sh
cobo check
cobo sync
```

Do not edit the generated blocks by hand; update their Cobo inputs and re-render
them instead.
